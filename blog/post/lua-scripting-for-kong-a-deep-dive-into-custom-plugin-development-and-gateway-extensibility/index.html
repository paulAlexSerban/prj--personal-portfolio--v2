Introduction

Kong Gateway sits at the edge of your infrastructure - the single chokepoint through which every API request passes. Most teams install Kong, configure routes and services, bolt on a few bundled plugins like rate-limiting or JWT authentication, and call it a day. That works until it doesn't. The moment a business requirement falls outside the predefined plugin catalog - custom header enrichment, tenant-aware request routing, proprietary authentication schemes, real-time traffic shaping - teams hit a wall.

The answer to that wall is Lua. Kong is built on top of OpenResty, which embeds LuaJIT directly inside Nginx worker processes. This means your custom code runs in the same process, at the same speed, with the same event-loop model as Kong's core. There is no sidecar, no network hop, no serialization overhead. Your plugin participates in the request lifecycle as a first-class citizen - not as an afterthought bolted onto the side.

This article is a deep technical dive aimed at software engineers who already understand HTTP, API gateways, and basic Lua syntax. The goal is not to teach Lua from scratch, but to illuminate how Kong's plugin model works, how to write plugins that behave correctly under production load, and where the traps are. By the end, you will have a clear mental model of the system and practical patterns you can apply immediately.

Why Lua? The OpenResty Foundation

LuaJIT Inside Nginx: Not a Scripting Afterthought

Kong's choice of Lua is not arbitrary or merely historical. OpenResty - the project Kong is built on - was created by Yichun Zhang (agentzh) specifically to embed LuaJIT into Nginx's event-driven architecture. LuaJIT is one of the fastest dynamic language runtimes ever built, routinely benchmarking within a small constant factor of optimized C code on tight loops. More importantly, it integrates with Nginx's non-blocking I/O model via coroutines, allowing Lua code to perform network calls (to Redis, PostgreSQL, external APIs) without blocking the Nginx worker thread.

This is the key insight that separates OpenResty Lua from conventional embedded scripting: when your plugin code calls ngx.sleep(), reads from a socket, or queries a shared dictionary, the worker yields cooperatively, allowing other requests to proceed. This is structurally identical to how Node.js and Go handle concurrency at the I/O boundary - but it happens inside a battle-tested C web server. The result is a scripting environment that can handle tens of thousands of concurrent connections without the overhead of threads or processes.

The Lua Language Itself

Lua was designed in the early 1990s at PUC-Rio as an embeddable extension language. Its design priorities - small footprint, clean C API, straightforward semantics - make it ideal for embedding in larger systems. The language surface area is deliberately small: tables (the single data structure that implements arrays, dictionaries, objects, and modules), first-class functions, coroutines, metatables for operator overloading, and a minimal standard library. There is no class keyword, no native module system beyond require, and no extensive standard library. What looks like a weakness is a feature: the language gets out of the way and lets the host environment (OpenResty/Kong) provide the important APIs.

For engineers coming from Python or JavaScript, the most disorienting aspect of Lua is 1-based array indexing and the fact that nil in a table is semantically equivalent to an absent key - behavior that matters when working with Kong's configuration tables. The second adjustment is the module system: every Lua file is a module that returns a table, and require caches the result. Understanding this caching behavior is critical for shared state management in plugins.

Kong's Plugin Architecture and the PDK

The Plugin Development Kit

Kong exposes a stable, versioned API to plugin authors called the Plugin Development Kit (PDK). The PDK is a collection of Lua modules namespaced under kong.* that provide controlled access to the request, response, service context, logging infrastructure, and shared state. The full PDK reference is extensive; the most commonly used namespaces are:

  • kong.request - read headers, query parameters, body, method, path
  • kong.response - set response headers, status codes, body
  • kong.service.request - mutate the request being forwarded to the upstream
  • kong.service.response - read the upstream response before it is returned
  • kong.log - structured logging at configurable levels
  • kong.cache - L1/L2 caching with TTL and negative caching support
  • kong.ctx.shared - a per-request table shared across all plugin instances in the same phase

The PDK exists for a reason: it abstracts away the underlying Nginx variables and OpenResty APIs, providing a stable surface that does not break between Kong versions. Plugin authors who bypass the PDK and write directly against ngx.var, ngx.req, and OpenResty's lua-resty-* libraries will find their code fragile across upgrades. Use the PDK unless you have a measured, specific reason to go below it.

Plugin File Structure

A Kong plugin is a directory containing at minimum two Lua files: handler.lua and schema.lua. In practice, well-structured plugins add additional modules for separation of concerns.

my-plugin/
├── handler.lua        # Plugin logic - phase callbacks
├── schema.lua         # Configuration schema (types, defaults, validation)
├── daos.lua           # Optional: custom database entities (Kong DB abstraction)
└── migrations/
    └── 000_base_my_plugin.lua  # Optional: DB migrations for custom entities

The schema.lua file defines what configuration values the plugin accepts, their types, defaults, and validation rules. Kong uses this schema to validate plugin configurations submitted via the Admin API and to populate plugin.config in handler callbacks. A correct and defensive schema saves significant debugging time - mistyped configuration keys fail immediately at configuration time rather than silently at runtime.

-- schema.lua
local typedefs = require "kong.db.schema.typedefs"

return {
  name = "my-plugin",
  fields = {
    { consumer = typedefs.no_consumer },
    { protocols = typedefs.protocols_http },
    {
      config = {
        type = "record",
        fields = {
          { upstream_header = { type = "string", required = true, default = "X-My-Plugin" } },
          { ttl_seconds     = { type = "integer", required = false, default = 60, between = { 1, 3600 } } },
          { enable_logging  = { type = "boolean", required = false, default = false } },
        },
      },
    },
  },
}

The Plugin Lifecycle: Phases and Execution Order

Nginx Phases Mapped to Kong Callbacks

Every HTTP request processed by Kong passes through a sequence of Nginx processing phases. OpenResty exposes hooks into each of these phases, and Kong wraps them into named callbacks on your handler. Understanding this sequence - and what is and is not possible in each phase - is the most important conceptual investment you can make before writing production plugins.

The primary phases, in execution order for a proxied request, are:

PhaseHandler MethodPurpose
SSL certificate selectioncertificateDynamic cert selection per SNI
RewriterewriteEarly request mutation, before routing
AccessaccessAuthentication, authorization, rate limiting
Upstream response receivedheader_filterMutate upstream response headers
Upstream body streamingbody_filterMutate or buffer upstream response body
Request completelogAsync logging, analytics, metrics

The access phase is the workhorse of most plugins. At this point, Kong has selected the upstream service and route, the consumer has been identified (if authentication plugins run earlier), and the request has not yet been forwarded. This is where you perform authentication checks, inject headers, apply rate limits, or short-circuit with an early response via kong.response.exit().

The log phase runs after the response has been fully sent to the client. Code in log must not attempt to modify the response - but it can write to external systems, flush buffers, or update counters. Critically, I/O in log is still non-blocking: you can call Redis, post to a webhook, or write to a queue without delaying the client. The client connection is already closed; you are working in a detached context within the worker's event loop.

Phase Ordering Across Multiple Plugins

When multiple plugins are enabled on a route, Kong sorts them by their declared PRIORITY constant and executes them in descending order within each phase. A plugin with PRIORITY = 1000 runs before one with PRIORITY = 500. This matters: if your authentication plugin runs after a header-injection plugin, the injected headers may be absent when the authentication logic needs them.

-- handler.lua - priority declaration
local MyPlugin = {
  PRIORITY = 800,
  VERSION  = "1.0.0",
}

Kong's own bundled plugins follow a documented priority order. The rate-limiting plugin runs at priority 901, basic-auth at 1001, and the correlation-id plugin at 100001. When building custom plugins that interact with authentication state (e.g., kong.client.get_consumer()), ensure your plugin's priority is lower than the authentication plugins it depends on.

Building Your First Production-Grade Plugin

A Request Enrichment Plugin

The following example implements a plugin that enriches outbound requests with tenant metadata fetched from an in-process cache. This pattern appears frequently in multi-tenant SaaS architectures where upstream services need to know which tenant a request belongs to without performing their own lookup.

-- handler.lua
local kong = kong

local RequestEnrichment = {
  PRIORITY = 800,
  VERSION  = "1.1.0",
}

-- Called once per worker on startup; use for module-level initialization
function RequestEnrichment:init_worker()
  kong.log.debug("RequestEnrichment plugin initialized in worker ", ngx.worker.id())
end

function RequestEnrichment:access(conf)
  -- Retrieve the authenticated consumer set by an upstream auth plugin
  local consumer = kong.client.get_consumer()
  if not consumer then
    -- No consumer context - skip enrichment or return 401 depending on config
    if conf.require_consumer then
      return kong.response.exit(401, { message = "Authentication required" })
    end
    return
  end

  -- Use kong.cache for L1 (worker-local) + L2 (shared memory) caching
  local cache_key = "tenant_meta:" .. consumer.id
  local tenant_data, err = kong.cache:get(cache_key, { ttl = conf.ttl_seconds }, function()
    -- This callback is called only on a cache miss
    -- In a real plugin, this would query a database or call an internal service
    -- using a lua-resty-http or lua-resty-redis client
    return fetch_tenant_metadata(consumer.id)
  end)

  if err then
    kong.log.err("Failed to fetch tenant metadata for consumer ", consumer.id, ": ", err)
    -- Fail open or fail closed depending on your risk tolerance
    if conf.fail_on_error then
      return kong.response.exit(503, { message = "Service temporarily unavailable" })
    end
    return
  end

  if not tenant_data then
    return
  end

  -- Inject enriched headers into the upstream request
  kong.service.request.set_header(conf.upstream_header .. "-Tenant-ID",   tenant_data.tenant_id)
  kong.service.request.set_header(conf.upstream_header .. "-Plan",         tenant_data.plan)
  kong.service.request.set_header(conf.upstream_header .. "-Region",       tenant_data.region)

  -- Store for use in the log phase
  kong.ctx.shared.tenant_data = tenant_data
end

function RequestEnrichment:log(conf)
  local tenant_data = kong.ctx.shared.tenant_data
  if not tenant_data or not conf.enable_logging then
    return
  end

  kong.log.info("Request processed for tenant=", tenant_data.tenant_id,
                " plan=", tenant_data.plan,
                " status=", kong.service.response.get_status())
end

return RequestEnrichment

Implementing the Tenant Fetch Function

The fetch_tenant_metadata function referenced above deserves its own treatment. In a real plugin, this would live in a separate module and use a non-blocking HTTP or database client from the OpenResty ecosystem:

-- tenant_client.lua - imported with require() in handler.lua
local http = require "resty.http"   -- lua-resty-http, bundled with Kong

local _M = {}

function _M.fetch_tenant_metadata(consumer_id)
  local httpc = http.new()
  httpc:set_timeout(200)  -- 200ms hard timeout; keep this tight

  local res, err = httpc:request_uri("http://internal-tenant-service/api/tenants/" .. consumer_id, {
    method  = "GET",
    headers = {
      ["Accept"]        = "application/json",
      ["X-Internal-Key"] = os.getenv("INTERNAL_API_KEY"),
    },
  })

  if not res then
    return nil, "HTTP request failed: " .. (err or "unknown error")
  end

  if res.status ~= 200 then
    return nil, "Upstream returned status " .. res.status
  end

  local cjson = require "cjson.safe"
  local data, parse_err = cjson.decode(res.body)
  if not data then
    return nil, "JSON parse error: " .. (parse_err or "unknown")
  end

  return data
end

return _M

Note the explicit 200ms timeout. In a gateway context, every synchronous operation in the hot path adds to tail latency. External calls during access phase add that latency to every request that hits a cache miss. This is why the caching layer is non-negotiable - the external call should be rare, not the common case.

Advanced Patterns: Shared State, Caching, and External Calls

The Three Levels of State in OpenResty

Understanding state boundaries in OpenResty is essential for writing correct plugins. There are three levels, with different scope and lifetime:

1. Local variables in phase callbacks - the most ephemeral form. These exist only within a single phase execution for a single request. Use these for intermediate computation. They are garbage-collected after the phase completes. 2. kong.ctx.shared - a per-request table that persists across all phases of a single request-response cycle. Values written in access are readable in header_filter, body_filter, and log. This table is reset for every new request. Use this for passing data between phases without re-computation. 3. ngx.shared.DICT (shared dictionaries) - shared across all worker processes via shared memory. This is the foundation of Kong's L2 cache. Access is serialized (a spinlock at the C level), so operations must be brief. Shared dictionaries are declared in the Nginx configuration with a fixed size; they use LRU eviction when full. Data stored here must be a Lua string or number - complex tables must be serialized with cjson before storage.

Kong's kong.cache abstraction manages a two-level system: L1 is a worker-local Lua table (zero IPC overhead, fastest), and L2 is a ngx.shared.DICT visible to all workers. A write to L2 invalidates L1 caches in other workers. This design means cache invalidation in Kong is eventually consistent across workers on the same node, and Kong Hybrid Mode introduces additional propagation considerations for multi-node deployments.

Timer-Based Background Work

Some plugin requirements cannot be satisfied in the hot request path. Consider a plugin that needs to aggregate metrics and push them to a monitoring system every 30 seconds. Doing this inline would add latency to every N-th request. OpenResty provides ngx.timer.at and ngx.timer.every for background tasks:

-- In init_worker, schedule a recurring background task
function MyPlugin:init_worker()
  local ok, err = ngx.timer.every(30, function(premature)
    if premature then
      -- Worker is shutting down; clean up and return
      return
    end
    flush_metrics_to_prometheus()
  end)

  if not ok then
    kong.log.err("Failed to start metrics flush timer: ", err)
  end
end

The premature flag is critical. When Nginx shuts down a worker, it fires all pending timers with premature = true. Ignoring this flag and attempting network I/O during shutdown can cause indefinite hangs that delay graceful restarts. Always check premature before performing any I/O in a timer callback.

Trade-offs and Common Pitfalls

Coroutine Yield Points Are Invisible

The most insidious class of bugs in OpenResty Lua plugins comes from misunderstanding where coroutine yield points occur. Yield points are any call that performs I/O: ngx.sleep, socket reads/writes, shared dictionary operations under contention, and calls into C libraries that block. Between yield points, Lua code runs atomically within the event loop. This is good for correctness - you cannot have data races on local variables - but it means a tight CPU-bound loop will block the entire worker for its duration.

A plugin that does JSON parsing of multi-megabyte bodies, complex cryptographic operations, or recursive table processing without yielding will degrade gateway throughput globally, not just for the single request being processed. If you need CPU-intensive work, either keep it bounded (hard size limits on bodies you'll process), move it to the log phase where it doesn't block the client response, or offload it via a timer to a background context.

Table Mutation and Schema Defaults

Kong's plugin configuration is passed as a Lua table to each phase callback. This table is shared - it is not copied per invocation. Mutating conf inside a callback introduces a subtle data corruption bug that manifests inconsistently under concurrent load:

-- WRONG: mutates shared config table
function MyPlugin:access(conf)
  conf.processed_header = string.upper(conf.upstream_header)  -- BUG
  kong.service.request.set_header(conf.processed_header, "value")
end

-- CORRECT: derive local values
function MyPlugin:access(conf)
  local processed_header = string.upper(conf.upstream_header)
  kong.service.request.set_header(processed_header, "value")
end

This bug does not surface in unit tests or low-concurrency environments. It surfaces in production under load, causing headers to be set to incorrect values for random requests. Always treat conf as read-only.

The Cost of require in Hot Paths

The first call to require("some.module") in a Lua VM executes the module file and caches the result. Subsequent calls return the cached table at near-zero cost. However, if a module is first required inside a hot phase callback rather than at the module level, the first few requests per worker incur the full module load cost - including disk I/O and LuaJIT compilation. This is not a catastrophic performance issue for most modules, but it is unnecessary noise.

-- SUBOPTIMAL: require inside the hot path
function MyPlugin:access(conf)
  local cjson = require "cjson"  -- cheap after first call, but still a hash lookup
  -- ...
end

-- PREFERRED: module-level require
local cjson = require "cjson"

local MyPlugin = { PRIORITY = 800, VERSION = "1.0.0" }

function MyPlugin:access(conf)
  -- cjson is already loaded and available as an upvalue
end

Body Access Has Consequences

Reading the request body in the access phase requires calling kong.request.get_body() or the lower-level ngx.req.read_body(). This buffers the entire request body into memory (or to a temp file if it exceeds client_body_buffer_size). For streaming use cases or large file uploads, this can dramatically increase memory usage and introduce latency. Always apply a size gate before reading bodies:

function MyPlugin:access(conf)
  local content_length = tonumber(kong.request.get_header("Content-Length"))
  if content_length and content_length > conf.max_body_size then
    return kong.response.exit(413, { message = "Request body too large" })
  end

  local body, err, mime_type = kong.request.get_body()
  -- ...
end

Testing and Debugging Lua Plugins

Busted and Kong's Test Harness

Kong's official testing infrastructure is built on Busted, a Lua unit testing framework, combined with lua-resty-test and Kong's own spec.helpers module that can spin up a real Kong instance in test mode. The three testing layers are:

Unit tests - test pure Lua functions in isolation, mocking PDK calls with stub tables. These are fast and catch logic errors early. Use the kong = require "spec.helpers".kong mock or hand-roll a stub for the PDK namespace your plugin uses.

Integration tests - spin up a real Kong instance using spec.helpers.start_kong(), configure routes, services, and plugin instances via the Admin API, then make real HTTP requests and assert on responses. These tests catch phase ordering bugs, schema validation issues, and interactions with other plugins.

Performance tests - use wrk, k6, or Locust to measure the latency impact of your plugin under load. Establish a baseline with the plugin disabled, then measure the overhead introduced by each phase callback. Even a "lightweight" plugin can add 1-2ms under certain conditions; under 50k req/s, that aggregates.

-- Example unit test with Busted
describe("RequestEnrichment plugin", function()
  local handler, conf

  before_each(function()
    handler = require "kong.plugins.request-enrichment.handler"
    conf = {
      upstream_header = "X-Tenant",
      ttl_seconds     = 60,
      fail_on_error   = false,
      enable_logging  = false,
    }
    -- Mock the PDK
    _G.kong = {
      client  = { get_consumer = function() return { id = "consumer-123" } end },
      cache   = { get = function(_, _, _, cb) return cb() end },
      service = { request = { set_header = spy.new(function() end) } },
      ctx     = { shared = {} },
      log     = { err = function() end, info = function() end, debug = function() end },
      response = { exit = function(status, body) error("exit:" .. status) end },
    }
  end)

  it("injects tenant headers when consumer is present", function()
    -- Arrange: mock fetch to return test data
    -- Act
    handler:access(conf)
    -- Assert
    assert.spy(kong.service.request.set_header).was.called_with(
      "X-Tenant-Tenant-ID", match._
    )
  end)
end)

Logging and Introspection

Kong's structured logging is the primary debugging tool for production plugins. Use the log levels appropriately: kong.log.debug for verbose traces (disabled in production), kong.log.info for normal operational events, kong.log.warn for recoverable anomalies, and kong.log.err for failures that degrade functionality. All log entries include the request ID automatically, making correlation across phases straightforward.

For transient debugging during development, ngx.say() in the access phase will short-circuit the request and return the output directly to the client - useful for inspecting variable state without modifying actual response paths. Remove these before committing.

Best Practices for Production Deployments

Version and Package Your Plugins as LuaRocks

Custom plugins should be packaged as LuaRocks packages (*.rockspec) and installed via luarocks install during container image build time. This provides dependency management, versioning, and reproducible builds. It also aligns with Kong's official plugin installation documentation and makes plugin lifecycle management - including upgrades and rollbacks - operationally straightforward.

Avoid the temptation to mount plugin files as ConfigMap volumes in Kubernetes and hot-reload them. Kong does not support hot-reloading of Lua code; workers cache require-d modules at startup. A code change requires a rolling restart of the Kong deployment, which should be coordinated through standard CI/CD practices, not sidestepped.

Fail Safely and Communicate Intent

Every plugin that makes external I/O calls must define explicit behavior for failure modes: should a Redis timeout cause the request to be rejected, or should it proceed without the enrichment? Neither choice is universally correct; it depends on whether the plugin provides a security control (fail closed) or an enhancement (fail open). Document this decision in code comments and expose it as a configuration option where appropriate.

When rejecting requests from a plugin, use consistent error shapes. Define a module-level error response formatter that matches your API's standard error schema. Wildly different error shapes from the gateway versus the upstream API create confusion for API consumers and complicate client-side error handling.

Observability as a First-Class Concern

Every non-trivial plugin should emit metrics. Kong's StatsD and Prometheus plugins aggregate gateway-level metrics, but they know nothing about your custom plugin's internal behavior: cache hit rates, upstream call latencies, tenant lookup failures. Use kong.log with structured fields and ship logs to your log aggregation platform (Elasticsearch, Loki, Splunk) where you can build custom queries and dashboards. For real-time metrics, consider writing to a shared dictionary counter that a background timer flushes to StatsD.

Consider adding a per-plugin health indicator: a shared dictionary key that records the last successful external call timestamp. A monitoring script can expose this via a custom health endpoint, enabling alerting before failures cascade into user-visible errors.

80/20 Insight: The Core Concepts That Matter Most

Lua scripting for Kong has significant surface area - the OpenResty API, the PDK, Nginx internals, LuaJIT specifics, testing frameworks - but 80% of practical plugin work reduces to five foundational concepts:

1. Phase selection is your most important architectural decision. Getting the right phase wrong - doing authentication in header_filter, or response mutation in access - produces bugs that are difficult to diagnose. Map your requirements to phases first, then write code.

2. kong.cache is not optional for any plugin that calls external services. Every external call in the hot path without caching is a latency multiplier and a reliability risk. Design your cache invalidation strategy before writing the fetch logic.

3. Never mutate conf or module-level state inside phase callbacks. Treat all shared tables as read-only within callbacks. Derive local copies for any values that need transformation.

4. Timeouts must be explicit and tight. The gateway is not the place for 5-second external call timeouts. Set aggressive timeouts (100-500ms), implement fallbacks, and test failure paths as thoroughly as the happy path.

5. The log phase is for asynchronous work. Any non-critical I/O - analytics, audit logging, metric flushing - belongs in log or in timer-driven background tasks. Keeping access and header_filter lean protects your P99 latency.

Key Takeaways

5 practical steps to apply immediately:

  1. Scaffold your plugin with Kong's official generator (kong plugin create <name>) to get a correct directory structure and schema skeleton. Do not hand-craft the directory structure from scratch.

  2. Write your schema.lua first, before any handler code. Defining types, defaults, and validation constraints before implementation prevents an entire class of runtime bugs and documents the plugin's configuration contract explicitly.

  3. Implement init_worker for all expensive module initialization - pre-compiling regular expressions, establishing connection pools, loading large lookup tables. Code in init_worker runs once per worker at startup, not on every request.

  4. Add a kong.log.debug trace at the entry and exit of every phase callback during development. Strip or gate these behind conf.debug_mode before production deployment. The habit of structured tracing makes bugs dramatically easier to isolate.

  5. Run your plugin through Kong's integration test harness with chaos conditions: introduce artificial delays and errors in your external dependencies and verify that the fail-open or fail-closed behavior you intended is what actually occurs under load.

Conclusion

Lua scripting transforms Kong from a configurable proxy into a programmable infrastructure layer. The combination of LuaJIT's performance, OpenResty's non-blocking I/O model, and Kong's well-designed PDK means that custom plugins are not a compromise - they are a first-class mechanism for encoding your organization's specific API governance, enrichment, and observability requirements directly into the gateway.

The learning curve is real. Developers accustomed to Python or JavaScript will need to internalize the coroutine-based concurrency model, the table-as-everything data model, and the phase-based execution context. These concepts are not difficult, but they are unfamiliar, and the failure modes for getting them wrong are often subtle and load-dependent.

The investment pays off quickly. A well-written Kong plugin replaces what would otherwise be a sidecar service, an application-level middleware library that every upstream service must independently implement, or a complex infrastructure workaround. It runs at the edge, at LuaJIT speed, in the same process as the gateway, with zero additional deployment overhead. For teams building on Kong, Lua is not an optional enhancement - it is the mechanism by which the gateway becomes genuinely yours.
